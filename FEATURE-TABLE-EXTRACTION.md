# Feature: Table Extraction from Articles

## Requirement

When the user pastes an article via the paperclip icon in the e-reader:

1. The app already extracts images from the article HTML
2. The app sends all content (text + images) to the model

**New behavior:** If the article contains tables (markdown format), then:
1. Extract the tables from the article HTML
2. Clean up and format them to look presentable
3. Render each table as an image (PNG)
4. Send these table images to the model along with the other extracted images

## Key Point

This happens at **article ingestion time** (when pasting), NOT after the model responds. The tables come from the **source article**, not from Claude's output.

## Current Flow

```
User pastes article URL
     ↓
Fetch HTML content
     ↓
Extract images from HTML → Store in Supabase
     ↓
Send HTML + images to model
     ↓
Model generates summary
```

## Proposed Flow

```
User pastes article URL
     ↓
Fetch HTML content
     ↓
Extract images from HTML → Store in Supabase
Extract tables from HTML → Render as PNG → Store in Supabase
     ↓
Send HTML + all images (including table images) to model
     ↓
Model generates summary
```

## Implementation Notes

- Tables in source articles are typically HTML `<table>` elements
- Need to detect, parse, and render tables during the image extraction phase
- Reuse existing image storage infrastructure (`article_charts` table, Supabase storage)

**Status:** Failed

**What was implemented:**
1. Added satori + resvg imports to `extract-images/+server.ts`
2. Added `extractTables()` function to parse HTML `<table>` elements using cheerio
3. Added `buildTableJsx()` to create satori-compatible JSX structure
4. Added `renderTableToImage()` to convert tables to PNG using satori + resvg
5. Modified POST handler to process tables after images (step 5b)
6. Tables get same treatment as images: storage, thumbnails, Anthropic upload

**Test case:**
- Pasted article containing several markdown tables via paperclip icon

**Observations:**
1. **Source article tables:** Markdown tables in the original article were NOT extracted or rendered as images. They did not appear in the canvas.
2. **Model-generated tables:** Tables generated by Claude in its response remained inline in the chat pane, rendered poorly with misaligned columns in the 450px width.

**Probable root causes:**
1. The implementation looks for HTML `<table>` elements, but the article content may be arriving as markdown (pipe-formatted tables) rather than rendered HTML
2. The extract-images endpoint may not be receiving the article content in the expected format
3. No server-side logging was added to confirm whether tables were detected

**Next steps to debug:**
1. Add console.log in `extractTables()` to verify it's being called and what HTML it receives
2. Check what format the article HTML actually contains (HTML tables vs markdown tables)
3. If articles arrive as markdown, need to parse markdown table syntax (`| Header | Header |`) instead of HTML `<table>` elements
4. For model-generated tables: separate feature still needed (FEATURE-TABLE-TO-CANVAS.md)

**Known issue - bottom border cut off:**
Some tables have their bottom border (emerald green) cut off in the rendered PNG.

Attempted fix: Increased `rowHeight` from 36 to 38 and buffer from 4 to 6 in `renderTableToImage()`. This made it worse - cut off most of the last row instead of just the border. Reverted.

The issue is in the satori height calculation: `(rows.length + 1) * 36 + 4`. The actual rendered content may exceed this calculated height. Root cause needs further investigation.
